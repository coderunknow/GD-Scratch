# neon_dash / GD-Scratch v0.2.1 verification report

**Release focus:** frame-rate correctness (a measured same-speed game at any
render rate), input-semantics hardening, a measured reduction of per-frame
interpreter work, player-reported fixes (unfair block-edge deaths, the
settings highlight cutting through the value pills, choppiness on weak
devices), and new in-game settings rows (LOW LATENCY, GRAPHICS, SHOW FPS).

**Compared baseline:** the v0.2.0 release archives (commit `cb8d4cf` tree,
rebuilt byte-identically from the generator) plus that same commit's tests.
The baseline `.sb3` files live only as local measurement input under a scratch
directory; they are not added to the repository.

## 1. What changed

- Replaced the "physics advances once per rendered frame" master loop with a
  **fixed 30 Hz simulation and a frame-time accumulator**. Rendering (paint,
  paint hud, parallax, particles, screen shake) still happens once per rendered
  frame; physics steps run 0–2 times per frame at 30 fps, exactly 2 times per
  frame at a locked 60 fps, and are capped (see §7).
- Added a **render-cadence input latch**: transient taps are latched when seen
  and consumed by exactly one physics step, so a tap held for a single render
  frame at 60 fps can never be lost, and a tap can never drive two steps.
- **Block corner forgiveness (owner-directed collision-rule change).** A fall
  whose bottom sits up to `CORNER_FORGIVE = 9` px (⅓ cell) past a block's
  surface when the overlap starts now snaps on top instead of killing. Applied
  identically to the Python reference (`verify.py`, `levels.py`) and the game
  (`game.py`) — they remain transcription-equal.
- **Settings redesign: 7 rows.** MUSIC / SOUND EFFECTS / PARTICLES / LOW
  LATENCY / GRAPHICS / SHOW FPS / BACK, with a wider highlight costume on this
  screen so the row highlight covers the value pill:
  - LOW LATENCY — the render-cadence tap latch, now switchable (default ON;
    OFF = classic 30 Hz sampling).
  - GRAPHICS — HIGH (default, unchanged) / LOW (far parallax layer retired,
    every particle burst halved) / ULTRA (far parallax retired, no particles).
  - SHOW FPS — a live render-fps readout (top right, ~2 updates/s) in play.
- Text pool grown 48 → 56 glyph clones so the settings values (slots 1–25)
  and the FPS overlay (49–54) never collide with the play HUD (1–46).
- Rebuilt the TurboWarp archive's pacing contract: both archives run the same
  30 Hz simulation; the TurboWarp `runtimeOptions` (60 fps + interpolation)
  only smooths rendering.
- New tests: `replay.js` dual-rate invariants, `physics.js` (coin/ring
  mechanics the solver never touches, plus the corner-forgiveness regression),
  `fuzz.js` + `tools/fuzz_ref.py` (differential fuzzer against the Python
  reference), `text.js` (glyph-pool consistency), extended `menus.js`
  (settings, pause/resume input hygiene, death-screen keys, win-screen input
  lock, best-progress records, music restarts), and the `level1_detail_low`
  benchmark scenario.
- `tools/audit_project.py` now accounts for sounds played through a variable
  menu (`playedViaVariable`).
- Build: zip entry timestamps are pinned, so two builds of one source tree are
  bit-identical.

Level maps, jump/pad/orb/portal physics, and speed are unchanged except the
single forgiveness rule above; all three solver solutions still replay
frame-exactly at 30 and 60 fps.

## 2. Stability fixes

Fix blocks follow the same schema as v0.2.0.

### Confirmed: the game ran at double speed on a 60 fps render clock

```text
Issue:       Level timers, scroll speed, physics and every countdown ran 2x
             as fast whenever the project ran at 60 fps (TurboWarp with the
             shipped runtimeOptions, or any host at 60 fps).
Reproduction: replay.js against the v0.2.0 stock archive with a deterministic
             60 fps clock: the level-1 solution finished in 659 render frames
             instead of 659 physics steps spread over 1318 render frames; all
             659 render frames ran a physics step. The TurboWarp archive on
             level 3 showed the same pattern (869/869). Menu timings halved
             too: win input lock ~44 render frames vs ~22 at 30 fps; death
             countdown ~84 vs ~42.
Expected:    One simulation speed at any render rate.
Observed:    Physics stepped once per rendered frame - the simulation clock
             was the render clock.
Root cause:  The v0.2.0 master loop ran `step play` (and every per-step
             countdown) once per `_step()` render tick with no notion of
             elapsed time.
Fix:         Fixed 30 Hz simulation (§7).
Verification: replay.js asserts, for all three fixtures on both archives at
             30 and 60 fps: identical physics traces, identical step counts
             (659/746/869), 60 fps takes exactly 2x the render frames
             (1318/1492/1738), no skipped or duplicated steps. A transient
             1-render-frame tap that spans no physics step at 60 fps is
             consumed exactly once.
```

### Confirmed: a tap made while paused leaked into the simulation on resume
(introduced during this release's development, caught before release)

```text
Issue:       Resuming from pause let the resuming keypress (or any tap made
             while paused) act as a jump on the first play step.
Reproduction: Rebuilt the source with only the fix reverted: pause with P,
             resume with space; the first `step play` after resume consumed
             held=1/jumpEdge=1 and the cube jumped (py -105 -> -35,
             airborne).
Expected:    The tap that resumes play is menu input, not gameplay input.
Observed:    The latch survived the pause/resume state transition.
Root cause:  The input latch was cleared when a level starts but not on the
             two pause->play resume paths.
Fix:         Both resume paths (the P key's pause branch and the pause
             menu's RESUME row) clear the latch.
Verification: menus.js asserts both resume paths at 30 and 60 fps; the
             capture wrapper records the exact held/jumpEdge the first play
             step consumes. Pre-fix build fails both checks; released
             archives pass.
```

### Owner-reported: deaths at block edges with "no spike touched"

```text
Issue:       Dying when landing next to / on a block platform edge, even
             though no hazard was visibly touched.
Reproduction: Level 1 fixture solution + one extra tap on step 271: the cube
             falls onto a block corner with its bottom 2.4 px below the
             surface at step 282 and died there under the old rule
             (reproduced on a pre-fix archive: dead@283).
Expected:    A near-miss corner clip should land, GD-style; only square wall
             hits and hits from below should kill.
Observed:    The landing condition required the bottom to already be at or
             above the surface before the step (epsilon tolerance only) -
             any 1 px clip killed.
Root cause:  The designed rule was stricter than the game it imitates; the
             owner classified it as a bug (2026-09-28), which authorizes the
             one collision-rule change.
Fix:         Landing tolerance widened to CORNER_FORGIVE = 9 px in verify.py
             and mirrored in game.py. Wall hits (bottom far below the
             surface), hits while rising, and ceiling-side equivalents are
             unchanged.
Verification: The corner schedule now lands (grounded, y=-75 at step 283)
             and still wins on step 659 - asserted in physics.js at 30 and
             60 fps against the reference trace. The differential fuzz
             (§8) matches the Scratch side to the new reference everywhere
             it is run. The three fixture replays are trace-identical (the
             rule only changes frames that used to die), so all stored step
             counts and win frames hold.
```

### Owner-reported: settings highlight "not long enough"

```text
Issue:       The yellow row highlight stopped in the middle of the ON/OFF
             value pill on the settings screen.
Reproduction: Open SETTINGS; the highlight spanned x=-125..+125 while the
             value pill spans x=90..162.
Root cause:  The Sel sprite used one 250 px costume for every screen.
Fix:         Second costume selWide (360 px) selected on the settings screen
             only, via a mirror variable so the costume (and the renderer
             dirty flag) only changes when the screen kind changes.
Verification: menus.js asserts the wide costume on SETTINGS and the narrow
             one everywhere else; geometry: pill right edge 162 < 180 =
             selWide right edge.
```

### Confirmed: zip container nondeterminism

`writestr` defaulted zip timestamps to "now"; builds of identical sources
differed in bytes. Entry timestamps are pinned; two consecutive builds are
bit-identical (`cmp` clean, both variants).

## 3. Performance work

- **Redraw pressure.** Redraw requests per frame dropped by 62–88% versus
  v0.2.0 (e.g. level 1 replay 90.65 → ~25 per frame, menu idle 26 → 2).
- **Render/update split.** Per-render-frame work no longer includes physics
  bookkeeping on frames that run no step; at a locked 60 fps the two steps
  per frame are grouped.
- **GRAPHICS settings** move real work off the renderer: LOW retires the far
  parallax layer (two wide sprites) and halves particle bursts; ULTRA
  removes particles entirely. The interpreter-side saving is small (~2%);
  the saving is composite/draw-side, which headless numbers cannot show.
- Investigated and **not** adopted: removing the master-clock redraw trick
  (forbidden), replacing `control_wait` (forbidden), narrowing the tile
  spawn scan (already amortized to zero on caught-up frames), caching HUD
  join strings (the change-detection guard already skips redundant
  repaints).

## 4. Runtime bugs

### Confirmed and fixed

- Pause/resume input leak (§2).
- Block corner deaths (§2, owner-directed rule change).
- Settings highlight width (§2).
- Zip container nondeterminism (§2).

### Investigated but not defects

- `die()` ordering (death particles vs generation counter): particles are
  lifetime-based (`repeat until life < 1`, then delete), not
  generation-tagged; a boom racing an R-restart leaves only short-lived
  (≤30 frame) cosmetic particles. Verified the Fx sprite does spawn bursts
  (an audit probe initially filtered a wrong sprite name — test bug, fixed).
- Level-select glyph clones report `size = 100` while the text variable says
  110 under the headless VM: `RenderedTarget.setSize` only assigns the size
  when a renderer is attached. Identical on the v0.2.0 baseline; in a real
  player `set size` applies.
- The jump branch performs no extra work (one SFX broadcast); no per-jump
  interpreter spike exists. The reported choppiness is renderer-side load,
  addressed by the GRAPHICS settings.
- Sounds played through a variable menu (`track`) are reported by
  `audit_project.py` under `playedViaVariable`, not as orphans.

### Known remaining limitations

- Sprite **size is unverifiable headless**; every other glyph property
  (costume, x, y, visibility) is asserted by text.js.
- The harness has no renderer and no audio engine, so this report makes no
  claim about rendered smoothness, audible output, or real-browser input
  latency; those need a human in Scratch Desktop / TurboWarp.
- The out-of-bounds safety death (`py` beyond ±210) is transcription-checked
  but not test-driven (unreachable on these levels' solver paths).
- TurboWarp's own CBF / fps / interpolation knobs live in the player, not
  the project: LOW LATENCY is the in-project analog, and SHOW FPS displays
  the host's render cadence — it cannot set a target.
- Settings are per-run (projects cannot persist variables without
  extensions). Toggling GRAPHICS to HIGH mid-level respawns the far parallax
  only at the next level start/restart; LOW/ULTRA take effect immediately.
- The TurboWarp archive relies on TurboWarp honoring `runtimeOptions.fps`;
  if it does not, the game now simply runs at that host's cadence at the
  same 30 Hz sim speed — no speed dependence remains, only smoothness.

## 5. The new settings in detail

| Row | Values | Effect |
|---|---|---|
| MUSIC / SOUND EFFECTS / PARTICLES | ON / OFF | carried over from v0.2.0 |
| LOW LATENCY | ON / OFF | ON: taps are latched at render cadence and consumed by exactly one physics step (default). OFF: inputs are sampled at 30 Hz only — a tap shorter than a physics step is dropped. |
| GRAPHICS | HIGH / LOW / ULTRA | LOW retires the far parallax layer and halves every particle burst; ULTRA additionally disables particles entirely. |
| SHOW FPS | ON / OFF | draws `FPS n` (rounded, ~0.5 s averaging window) at the top right during play. |

All rows take effect immediately (except the HIGH parallax respawn noted
above) and reset to defaults on the green flag.

## 6. Architecture changes

### Fixed-step simulation clock

- Time source: the Scratch `timer` (chosen over `days since 2000`: it resets
  with the green flag alongside every other piece of run state, needs no
  epoch arithmetic, and is monotonic within a run).
- Each rendered frame: `now30 = floor(timer * 30)`, `due = min(now30 -
  lastTick, 3)`; at most 3 steps run per frame and any excess backlog is
  dropped, so a stalled tab or a slow device can never trigger unbounded
  catch-up — the game slows down uniformly instead of teleporting.
- Per step, the master tick re-reads state and runs exactly one of: `step
  play`, death-countdown decrement, win-lock decrement. Shake ticks and the
  menu tick are step-paced the same way.
- The `set x` redraw trick is kept - it is what makes caught-up frames
  nearly free.

### Input latch

- Render cadence: `raw = space | up | mouse down`; `tapLatch` sets on the
  0→1 edge; `rawPrev = raw`. LOW LATENCY OFF discards the latch instead of
  holding it for the next step (classic 30 Hz sampling).
- Per physics step: `held = raw + tapLatch`, `jumpEdge = (tapLatch == 1)`,
  then the latch clears. Grounded jumps use `jumpEdge`; held-jump-on-landing
  uses `held`.
- The latch clears on `start level` and on both pause→play resume paths.

### Clone lifecycle

Unchanged from v0.2.0 (generation checks retire world clones on exit; only
original sprites answer broadcasts).

## 7. Benchmark results

### Method

`tests/headless/bench.js` loads both archives into the same scratch-vm
harness on the same host and runs identical deterministic inputs (the Python
solver's schedules). Seven runs per scenario; medians of run medians for
wall-clock and exact per-frame primitive-call counts from the instrumented
pass. Headless workload comparison, not a rendered-FPS measurement.

Baseline: v0.2.0 archives, same harness, same host, same options.

| Scenario | Primitive calls / frame v0.2.0 → v0.2.1 | Redraws / frame | Median step ms | Peak clones |
|---|---:|---:|---:|---:|
| Menu idle | 972.7 → 590.2 (−39.3%) | 26.0 → 2.0 | 0.225 → 0.142 | 50 → 58 |
| Level 1 full solution replay | 2,690.6 → 1,723.3 (−36.0%) | 90.7 → 25.2 | 0.498 → 0.323 | 68 → 76 |
| Level 3 full solution replay | 2,686.1 → 1,706.4 (−36.5%) | 91.5 → 24.9 | 0.466 → 0.308 | 69 → 77 |
| Restart stress (20 R presses) | 2,734.7 → 1,796.2 (−34.3%) | 87.2 → 23.5 | 0.496 → 0.419 | 64 → 72 |
| Death/recovery cycle | 1,863.6 → 1,269.0 (−31.9%) | 107.1 → 41.8 | 0.415 → 0.278 | 80 → 87 |
| Pause/resume cycle | 1,557.9 → 1,052.6 (−32.4%) | 94.6 → 30.6 | 0.418 → 0.182 | 80 → 86 |
| Return to menu | 1,010.0 → 619.5 (−38.7%) | 26.9 → 2.6 | 0.162 → 0.106 | 57 → 63 |
| Level 1, GRAPHICS LOW | — (new scenario) | 23.1 | 0.300 | 74 |

Honest accounting, measured mid-development: the pacing redesign alone took
per-frame primitive work down 36–46% versus v0.2.0; the new settings
features (8 more always-alive glyph clones for the wider text pool, the fps
meter, the settings rows) add about 5–13% back. The shipped release is
therefore 32–39% below v0.2.0 in every scenario - far beyond the ≥3%
release target - with redraws down 62–88% and peak clones ≤87, well under
the 300-clone VM limit. Wall-clock medians are host-dependent; the
primitive/redraw/clone counts are machine-independent and are the stronger
evidence.

### Load and update measurements

- Startup/archive-load responsiveness: **not reliably measurable in this
  environment** (same finding as v0.2.0).
- Asset bytes: essentially unchanged (110 PNG / 13 WAV assets; the settings
  background PNG and the new selWide costume differ only in pixels).

## 8. Verification actually passed

All from the committed sources and committed `dist/*.sb3`.

- `tests/run_all.sh`, both archives: **all checks passed** (25 result
  lines): audio determinism; replay.js 3 fixtures × {30, 60} fps
  (trace-exact vs the Python reference; steps {659, 746, 869}; 60 fps
  exactly 2× frames {1318, 1492, 1738}; 1-frame tap consumed once);
  menus.js ×2 rates (~60 checks: 7-row settings, all toggles, wide
  highlight costume, GRAPHICS LOW/ULTRA live effects on parallax/particle
  clone counts, FPS overlay text, LOW LATENCY on/off tap semantics,
  pause/resume hygiene, death/win key handling, music restarts); text.js
  glyph pool ×2 rates; physics.js coin/ring/corner ×2 rates; fuzz.js ×2
  archives; lifecycle.js ×2 rates.
- **Differential fuzz evidence** (beyond the committed suite): 450
  schedules / 20,479 physics steps at 30 fps and 2 × 120 schedules / 5,410
  steps at 60 fps (both archives) — every step of every seeded random
  schedule matches `verify.py` exactly (y, vy, grounded, grav), with
  die/win events landing on the same steps. This covers random deaths,
  corner clips, portal misses and pad/orb interactions the fixtures never
  visit.
- RED→GREEN for the collision rule: a pre-fix archive dies at step 283 on
  the corner schedule; the released archive lands and wins at 659.
- `tools/audit_project.py` on both released archives: no dangling calls,
  no orphan sounds, no unreachable broadcasts (`playedViaVariable:
  ["track"]` is the intentional variable-menu music picker).
- Byte-determinism: two generator runs from one source tree produce
  bit-identical `.sb3` files (`cmp` clean), both variants.
- Stock compliance: `dist/GD-Scratch.sb3` has `"extensions": []` and stock
  blocks only; loading in the desktop app is a human step, not claimed
  here.
