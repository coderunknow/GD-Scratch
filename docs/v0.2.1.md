# neon_dash / GD-Scratch v0.2.1 verification report

**Release focus:** frame-rate correctness (a measured same-speed game at any
render rate), input-semantics hardening, and a measured reduction of per-frame
primitive work. Gameplay, level maps, physics constants and feel are unchanged:
all three solver solutions still replay frame-exactly, now at 30 fps *and*
60 fps render clocks.

**Compared baseline:** the v0.2.0 release archives (commit `cb8d4cf` tree,
rebuilt byte-identically from the generator) plus that same commit's tests.
The baseline `.sb3` files live only as local measurement input under a scratch
directory; they are not added to the repository.

## 1. What changed

- Replaced the "physics advances once per rendered frame" master loop with a
  **fixed 30 Hz simulation and a frame-time accumulator**. Rendering (paint,
  paint hud, parallax, particles, screen shake) still happens once per rendered
  frame; physics steps run 0–2 times per frame at 30 fps, exactly 2 times per
  frame at a locked 60 fps, and are capped (see §6).
- Added a **render-cadence input latch**: transient taps are latched when seen
  and consumed by exactly one physics step, so a tap held for a single render
  frame at 60 fps can never be lost, and a tap can never drive two steps.
- Rebuilt the TurboWarp archive's pacing contract: both archives now run the
  same 30 Hz simulation; the TurboWarp `runtimeOptions` (60 fps +
  interpolation) only smooths rendering.
- New tests: `replay.js` dual-rate invariants, `physics.js` (coin/ring
  mechanics the solver never touches), `text.js` (glyph-pool consistency),
  and extended `menus.js` coverage (pause/resume input hygiene, death-screen
  keys, win-screen input lock, best-progress records, music restarts).
- `tools/audit_project.py` now accounts for sounds played through a variable
  menu (`playedViaVariable`), so the `track` sound is no longer reported as
  never played.
- Build: zip entry timestamps are pinned, so two builds of one source tree are
  bit-identical (previously only the entry contents were deterministic; the
  container differed by wall-clock mtime).

No level maps, movement constants, collision rules, or gameplay semantics were
changed.

## 2. Stability fixes

Fix blocks follow the same schema as v0.2.0.

### Confirmed: the game ran at double speed on a 60 fps render clock

```text
Issue:       Level timers, scroll speed, physics and every countdown ran 2x
             as fast whenever the project ran at 60 fps (TurboWarp with the
             shipped runtimeOptions, or any host at 60 fps).
Reproduction: replay.js against the v0.2.0 stock archive with a deterministic
             60 fps clock: the level-1 solution finished in 659 render frames
             instead of 659 physics steps spread over 1318 render frames; all
             659 render frames ran a physics step (the clock wanted half of
             them). The TurboWarp archive on level 3 showed the same pattern
             (869/869). Menu timings halved too: win input lock ~44 render
             frames vs ~22 at 30 fps; death countdown ~84 vs ~42.
Expected:    One simulation speed at any render rate: physics time advances
             with wall-clock time, rendering cadence is free.
Observed:    Physics stepped once per rendered frame - the simulation clock
             was the render clock.
Root cause:  The v0.2.0 master loop ran `step play` (and every per-step
             countdown) once per `_step()` render tick with no notion of
             elapsed time.
Fix:         Fixed 30 Hz simulation (§6): each rendered frame accumulates
             elapsed time from the Scratch `timer`, runs the 0-2 due physics
             steps, caps catch-up at 3 steps and drops any further backlog.
Verification: replay.js asserts, for all three fixtures on both archives at
             30 and 60 fps: identical physics traces, identical step counts
             (659/746/869), 60 fps takes exactly 2x the render frames
             (1318/1492/1738), no skipped or duplicated steps. A transient
             1-render-frame tap that spans no physics step at 60 fps is
             consumed exactly once. menus.js win lock and death countdown now
             last twice as many render frames at 60 fps as at 30.
```

### Confirmed: a tap made while paused leaked into the simulation on resume
(v0.2.1-introduced, caught before release)

```text
Issue:       Resuming from pause let the resuming keypress (or any tap made
             while paused) act as a jump on the first play step.
Reproduction: Rebuilt the v0.2.1 source with only the fix reverted, then ran
             the menus.js resume scenario against it: pause with P, resume
             with space; the first `step play` after resume consumed
             held=1/jumpEdge=1 and the cube jumped (py -105 -> -35, airborne,
             grounded=0). The v0.2.0 baseline cannot show this (it had no
             input latch at all), so the defect is v0.2.1-introduced; it was
             found by the audit and fixed before release.
Expected:    The tap that resumes play is menu input, not gameplay input: the
             cube must still be standing (py=-105, grounded=1) and the first
             play step must see held=0, jumpEdge=0.
Observed:    The latch survived the pause/resume state transition.
Root cause:  The input latch was cleared when a level starts but not on the
             two pause->play resume paths.
Fix:         Both resume paths (the P key's pause branch and the pause menu's
             RESUME row) clear the latch.
Verification: menus.js asserts both resume paths at 30 and 60 fps; the
             capture wrapper records the exact held/jumpEdge the first play
             step consumes. At 60 fps the check waits for the first step
             (the resume frame may run none). Pre-fix archive fails both
             checks; released archives pass.
```

### Confirmed: progress records could be observed mid-write (audit finding, hardening)

The death path now records best progress inside the same atomic `die`
procedure as before, but the audit added regression coverage: dying mid-level
records `BESTS[level] > 0` and an `R` during the death screen restarts
immediately with the record intact (menus.js, both rates).

## 3. Performance work

Investigated, measured, and kept (details in §7):

- **Redraw pressure.** The old loop requested a redraw on essentially every
  primitive-heavy path; redraw requests per frame dropped by 62–88% across
  scenarios (e.g. level 1 replay 90.65 → 25.16 per frame, menu idle 26 → 2).
- **Render/update split.** Per-render-frame work no longer includes physics
  bookkeeping on frames that run no step; at a locked 60 fps the two steps per
  frame are grouped, so per-frame primitive work is what the render pass costs
  plus amortized simulation.
- Investigated and **not** adopted (would change visible behavior or violate
  constraints): removing the master-clock redraw trick (forbidden), replacing
  `control_wait` (forbidden), narrowing the tile spawn scan below the current
  8-columns-per-tick catch-up (measured cost already amortized to zero on
  caught-up frames by the spawnHi guard), caching `join(COINS , coins)` HUD
  strings (the change-detection guard already skips redundant repaints).

## 4. Runtime bugs

### Confirmed and fixed

- Pause/resume input leak (§2 above).
- Zip-container nondeterminism: pinned entry timestamps (§1 above).

### Investigated but not defects

- `die()` ordering (death particles vs generation counter): `boom` particles
  are lifetime-based (`repeat until life < 1`, then `delete clone`), not
  generation-tagged. A boom broadcast racing an R-restart therefore only ever
  leaves a handful of short-lived (≤30 frame) cosmetic particles, which expire
  on their own; only the original FX sprite answers the broadcast (isClone
  guard), and particle randomness never touches the simulation.
- Level-select glyph clones report `size = 100` while the text variable says
  110 under the headless VM: `RenderedTarget.setSize` only assigns the size
  when a renderer is attached, so size is not observable headless. Verified
  identical on the v0.2.0 baseline; in a real player `set size` applies.
- Sounds played through a variable menu (`track`) are reported by
  `audit_project.py` under `playedViaVariable`, not as orphans.

### Known remaining limitations

- Sprite **size is unverifiable headless** (above); every other glyph property
  (costume, x, y, visibility) is asserted by text.js.
- The scratch-vm harness has no renderer and no audio engine, so this report
  makes no claim about rendered smoothness, audible output, or real-browser
  input latency; those require a human in Scratch Desktop / TurboWarp.
- The out-of-bounds safety death (`py` beyond ±210) exists in both the Python
  reference and the game and is transcription-checked, but no test drives the
  cube out of the world: on these levels that requires missing a ceiling
  catch right after a gravity flip, which the solver never does.
- The TurboWarp archive relies on TurboWarp honoring `runtimeOptions.fps`;
  on hosts that ignore it the game now simply runs at that host's cadence at
  the same 30 Hz sim speed - there is no speed dependence left, only smoothness.

## 6. Architecture changes

### Fixed-step simulation clock

- Time source: the Scratch `timer` (chosen over `days since 2000`: it resets
  with the green flag alongside every other piece of run state, needs no
  epoch arithmetic, and both are monotonic within a run; `timer` is also the
  only one of the two that TurboWarp's interpolation layer keeps in step with
  rendering).
- Each rendered frame: `now30 = floor(timer * 30)`, `due = min(now30 -
  lastTick, 3)`; at most 3 steps run per frame and any excess backlog is
  dropped, so a stalled tab or a slow device can never trigger unbounded
  catch-up - the game slows down uniformly instead of teleporting.
- Per step, the master tick re-reads state and runs exactly one of: `step
  play`, death-countdown decrement, win-lock decrement. Shake ticks and the
  menu tick are step-paced the same way.
- The `set x` redraw trick (request a repaint on frames that ran no step) is
  kept - it is what makes caught-up frames nearly free.

### Input latch

- Render cadence: `raw = space | up | mouse down`; `tapLatch` sets on the
  0→1 edge; `rawPrev = raw`.
- Per physics step: `held = raw + tapLatch`, `jumpEdge = (tapLatch == 1)`,
  then the latch clears. Grounded jumps use `jumpEdge`; held-jump-on-landing
  uses `held` - both behave exactly as in v0.2.0.
- The latch clears on `start level` and on both pause→play resume paths, so no
  edge survives a state transition.

### Clone lifecycle

Unchanged from v0.2.0 (generation checks retire world clones on exit; only
original sprites answer broadcasts). Peak clone counts are unchanged or one
clone lower on the death/pause scenarios (§7).

## 7. Benchmark results

### Method

`tests/headless/bench.js` loads both archives into the same scratch-vm harness
on the same host and runs identical deterministic inputs (the Python solver's
schedules). Seven runs per scenario; the table reports the median of run
medians for wall-clock and the exact per-frame primitive-call count from the
instrumented pass. As in v0.2.0: this is a headless workload comparison, not a
rendered-FPS measurement on a player device; the primitive and redraw counts
are machine-independent and are the stronger evidence.

Baseline: v0.2.0 archives (committed dists of the `cb8d4cf` tree), same
harness, same host, same options.

| Scenario | Primitive calls / frame v0.2.0 → v0.2.1 | Redraw requests / frame v0.2.0 → v0.2.1 | Median step ms v0.2.0 → v0.2.1 | Peak clones v0.2.0 → v0.2.1 |
|---|---:|---:|---:|---:|
| Menu idle | 972.7 → 535.4 (−45.0%) | 26.00 → 2.00 | 0.225 → 0.246 | 50 → 50 |
| Level 1 full solution replay | 2,690.6 → 1,642.5 (−39.0%) | 90.65 → 25.16 | 0.498 → 0.340 | 68 → 68 |
| Level 3 full solution replay | 2,686.1 → 1,625.0 (−39.5%) | 91.52 → 24.98 | 0.466 → 0.307 | 69 → 69 |
| Restart stress (20 R presses) | 2,734.7 → 1,709.0 (−37.5%) | 87.17 → 23.53 | 0.496 → 0.297 | 64 → 64 |
| Death/recovery cycle | 1,863.6 → 1,192.6 (−36.0%) | 107.14 → 42.07 | 0.415 → 0.261 | 80 → 79 |
| Pause/resume cycle | 1,557.9 → 984.2 (−36.8%) | 94.59 → 31.27 | 0.418 → 0.189 | 80 → 78 |
| Return to menu | 1,010.0 → 549.8 (−45.6%) | 26.93 → 3.27 | 0.162 → 0.096 | 57 → 56 |

Primitive work per frame fell 36–46% in every scenario - far beyond the ≥3%
release target - and redraw requests fell 62–88%. Peak clone counts are equal
or lower everywhere and stay far under the 300-clone VM limit. Median step
time fell in six of seven scenarios; the menu-idle median is 0.021 ms higher
in this run, which is within this host's noise and contradicted by that
scenario's exact primitive count (972.7 → 535.4). The per-frame work
reduction is reproducible; wall-clock numbers are host-dependent.

### Load and update measurements

- Startup/archive-load responsiveness: **not reliably measurable in this
  environment** (same finding as v0.2.0; the target player UIs were not
  measured).
- Asset bytes: unchanged from v0.2.0 (110 PNG / 13 WAV assets; no asset work
  was attempted).
