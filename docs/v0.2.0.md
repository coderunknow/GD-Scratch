# neon_dash / GD-Scratch v0.2.0 verification report

**Release focus:** clone lifecycle stability, runtime correctness, repeatable
release assets, and measured reduction of restart/effect clone churn. No broad
gameplay rewrite or level redesign was made.

**Compared baseline:** project built from repository commit
`5548bae64d0496161c0b6829f3323f10f445d5a3` before the v0.2.0 changes. Both
`.sb3` variants were rebuilt from that same generator/toolchain for the
comparison. The v0.1 baseline archive is kept only as local measurement input;
it is not added to the repository.

## 1. What changed

- Prevented `Ground`, `Far`, and `FX` clones from responding to their parent's
  broadcast work. A clone-local `isClone` flag now lets only each original
  sprite handle `level start` or `boom`.
- Invalidated the world generation when leaving an active run for a menu/screen,
  so level tiles and parallax/floor clones are retired instead of running behind
  the menu.
- Added the previously unwired jump sound effect to accepted grounded jumps.
- Removed the `boot` broadcast, which had no receiver and performed no work.
- Seeded noise used by sound effects so repeated builds synthesize identical
  WAV payloads rather than varying asset hashes from the module-global RNG.
- Added an actual-VM clone lifecycle regression/stress test, a static project
  wiring audit, an audio determinism check, and a repeatable timing/opcode/clone
  benchmark.

No level maps, movement constants, collision rules, or existing control
semantics were intentionally changed.

## 2. Stability fixes

### Confirmed: restart broadcast caused exponential scenery clone growth

```text
Issue:       Ground and Far scenery populations multiplied on level restart.
Reproduction: Start level 1; press R repeatedly. Also verified by the lifecycle
              harness against the pre-fix archive.
Expected:     4 Ground strip clones and 2 Far parallax clones for one level.
Observed:     Under the 8-restart lifecycle test, the old archive reached the
              Scratch VM's 300-clone ceiling: 228 Ground and 26 Far clones.
Root cause:   Scratch broadcasts start matching hats on clones as well as on the
              original sprite. Each old Ground/Far clone received `level start`
              and ran the same clone factory as the original.
Fix:          Added clone-local `isClone`; only the original runs the broadcast
              handlers. Generation checks continue to retire older scenery.
Verification: Same 8-restart test: peak Ground=4, Far=2, 57 total clones at
              peak, no VM clone-limit exhaustion. The 20-restart benchmark
              peaked at 64 total clones (75 targets total), not 300.
```

### Confirmed: noise-based sound effects varied across identical builds

```text
Issue:       Rebuilding without gameplay/source changes produced different WAV
              bytes, content-addressed asset names, and project JSON.
Reproduction: Synthesize jump, portal, click, and win sounds twice in one
              process and compare their bytes; each pair differed before fix.
Root cause:   Those effects called noise() without an RNG, so it consumed
              Python's process-global random stream.
Fix:          Give each noise-based effect its own fixed, distinct seed.
Verification: The new generator check synthesizes all 13 project sounds twice
              and requires byte-for-byte equality; it passes. Separate clean
              builds of both final archives had identical member names and
              payload bytes (including project.json). The full build and VM
              suite also pass with the fixed audio assets.
```

### Confirmed: particle clones recursively spawned particle bursts

```text
Issue:       Repeated `boom` broadcasts multiplied active FX clones.
Reproduction: Set fxN=22 and issue six boom broadcasts four VM steps apart.
Expected:     At most one 22-particle burst per broadcast; old particles expire.
Observed:     Baseline peaked at 280 FX clones and still had 67 after a 90-step
              drain. The project was close to Scratch's 300-clone limit.
Root cause:   FX clones inherited the `boom` broadcast hat and each ran the
              particle factory when the next burst was broadcast.
Fix:          Restrict `boom` handling to the original FX sprite.
Verification: The same VM test peaked at 22 FX clones and had 0 remaining after
              the 90-step drain.
```

### Confirmed: leaving a run left world clones alive

```text
Issue:       Q returned to the menu but level scenery clones stayed live.
Reproduction: Start a level, then press Q and inspect scratch-vm targets.
Observed:     Baseline retained 254 Tile/Ground/Far clones after returning to
              the menu and advancing 10 VM steps.
Root cause:   `goto screen` changed the state/backdrop but did not change the
              generation used by world clones' retirement checks.
Fix:          Increment the world generation when leaving play/death/pause/win.
Verification: After Q and 10 VM steps the patched project has 0 Tile/Ground/Far
              clones; state is `menu`.
```

## 3. Performance work

### Restart/effect clone churn

- **Hot path:** repeated level starts and repeated visual-effect broadcasts.
- **Old behavior:** every extant broadcast-listening clone re-entered a clone
  factory; repeated restarts/effects amplified active target count and redraws.
- **Change:** Original-only broadcast handling plus generation invalidation on
  screen exit.
- **Why it helps:** restart work and redraw requests no longer scale with the
  number of prior scenery clones; effect bursts are bounded by `fxN` per event.
- **Gameplay impact:** level, physics, collision, and coin traces remain
  unchanged. Jump feedback was added without changing movement behavior.

Other per-frame systems were not rewritten: their repeated work did not show a
reproducible stability or performance problem in the measured scenarios.

## 4. Runtime bugs

### Confirmed and fixed

- Environment clone fan-out on restart — reproduced on baseline, fixed, and
  checked with eight restarts and a separate 20-restart benchmark.
- Recursive FX burst cloning — reproduced on baseline and fixed; bounded burst
  and lifetime cleanup verified in scratch-vm.
- Level/world clones surviving Q/menu exit — baseline retained 254 environment
  clones; patched run retained none after 10 steps.
- Jump sound effect was present in the project but had no sender. Static block
  wiring showed no `sfx jump` broadcast; baseline menu/runtime regression test
  failed to observe a sound-play call for a grounded jump. Added the broadcast
  at the accepted-jump branch; the current test observes `sfx jump` with SFX on.
- Sound asset nondeterminism: four effects consumed process-global randomness
  while synthesizing noise. Per-effect fixed seeds plus a byte-comparison check
  make all 13 generated sound payloads repeatable.
- Dead `boot` broadcast: no receiver and no side effect. Removed rather than
  keeping a silent no-op.

### Investigated but not reported as defects

- Other `forever` loops and broad static warnings were not changed just to
  silence analysis. The benchmark and scratch-vm scenarios did not provide
  evidence to replace the established master-clock/render-pacing design.
- No new collision, gravity, portal, pad/orb, or level-completion defect was
  reproduced by the deterministic replay suite.

### Known remaining limitations

- This environment has no Scratch editor/browser renderer or physical audio
  device. The tests verify the sound block is dispatched, not that a human
  listener hears it in a specific browser/audio configuration.
- No manual visual playthrough in scratch.mit.edu or the TurboWarp website was
  performed. Headless scratch-vm is the runtime evidence for this report.
- Solver traces cover known completion schedules; they are not exhaustive
  proofs of every player input or every edge condition.

## 5. Polish and features

- **Jump feedback:** a jump accepted from grounded state now sends the existing
  jump SFX. Reason: the asset and sound receiver already existed but no runtime
  path sent it; baseline observation confirmed silence at the block-dispatch
  layer. This is a small justified feedback fix, not a new gameplay system.
- **Exit cleanliness:** returning to menus now retires world scenery, avoiding
  stale gameplay objects behind menu presentation.
- No new mechanics or level content were added. This release intentionally
  spends scope on reliability and responsiveness.

## 6. Architecture changes

### Clone lifecycle

```text
Old subsystem: Broadcast handlers on clone-capable scenery/effect sprites.
Problem:       Scratch runs broadcast hats on clones; clone factories recursively
               multiplied Ground/Far strips and FX particles.
Incremental fix insufficient: Clamping clone creation would still leave the
               event fan-out and stale targets active, and could omit scenery.
New design:    A clone-local isClone flag is set by the as-clone hat. Only the
               original executes factory broadcast handlers. Environment clones
               retain generation-based retirement; exiting a run advances gen.
Expected benefit: Bounded clone populations and less needless interpreter/render
               work under repeated use.
Observed benefit: Restart stress fell from 300 to 64 peak clones, and six 22-FX
               bursts fell from 280 to 22 peak FX clones.
Compatibility: No Scratch extensions or TurboWarp-only features were added.
```

## 7. Benchmark results

### Method

`tests/headless/bench.js` loads both archives into the same scratch-vm harness.
For each scenario it runs seven untimed-instrumentation repetitions and reports
the median of the run medians, plus the median run mean/p95. A separate pass
counts Scratch primitive invocations, redraw requests, and target instances.
Each stress/replay workload uses deterministic menu/input flows. The benchmark
is a headless workload comparison, **not** a measurement of rendered FPS on a
player's device. Wall-clock results are noisy and host-specific; primitive and
clone counts are the stronger evidence here.

| Scenario | VM steps | Median step ms v0.1 → v0.2 | Primitive calls / step v0.1 → v0.2 | Redraw requests / step v0.1 → v0.2 | Peak clones v0.1 → v0.2 |
|---|---:|---:|---:|---:|---:|
| Menu idle | 60 | 0.150 → 0.175 | 972.7 → 972.7 | 26.00 → 26.00 | 50 → 50 |
| Level 1 full solution replay | 659 | 0.427 → 0.465 | 2,690.4 → 2,690.6 | 90.65 → 90.65 | 68 → 68 |
| Level 3 full solution replay | 869 | 0.413 → 0.432 | 2,686.4 → 2,686.3 | 91.69 → 91.62 | 69 → 69 |
| Restart stress (20 R presses) | 600 | 0.692 → 0.426 | 5,105.4 → 2,734.7 | 355.50 → 87.17 | 300 → 64 |
| Death/recovery cycle | 720 | 0.289 → 0.320 | 1,863.0 → 1,863.7 | 107.09 → 107.18 | 80 → 80 |
| Pause/resume cycle | 240 | 0.192 → 0.200 | 1,557.7 → 1,557.7 | 94.65 → 94.52 | 80 → 80 |
| Return to menu | 60 | 0.156 → 0.151 | 1,100.6 → 1,011.3 | 35.18 → 27.40 | 63 → 55 |

For the 600-step restart scenario, primitive work decreased by 2,370.7 calls
per step (about 46.4%); redraw requests decreased by 268.33 per step (about
75.5%). Peak clone count decreased by 236 (300 → 64), and peak targets by the
same amount (311 → 75). This measured improvement is concentrated in the
restart workload; ordinary gameplay/idle primitive work is effectively
unchanged. Restart-stress median step time also fell in this run (0.692 → 0.426
ms), but wall-clock timings are host-dependent. Several ordinary scenarios had
slightly higher medians in this run (level 1: 0.427 → 0.465 ms; level 3: 0.413
→ 0.432 ms; menu idle: 0.150 → 0.175 ms), while return-to-menu was slightly
lower (0.156 → 0.151 ms). These small, sub-millisecond differences are
inconclusive and do not support a generalized speedup or regression claim. The
reproducible improvement is the bounded clone/work reduction under restart
stress.

### Load and update measurements

- Startup/archive-load responsiveness: **not reliably measurable in this
  environment**. Single headless VM load samples varied substantially; the
  target Scratch/TurboWarp player UI was not measured.
- Generic update cost outside the named benchmark scenarios: **not reliably
  measurable in this environment**. Ten-frame samples were too short and noisy
  to support a general update-cost claim.
- PNGs/WAVs/asset bytes: 110 / 13 / 1,565,514 bytes for both archives; no asset
  payload reduction was attempted.

## 8. Verification actually passed

`./tests/run_all.sh` passed for both `dist/GD-Scratch.sb3` and
`dist/GD-Scratch-TurboWarp.sb3`:

- Level solver: all three levels remain completable.
- Generated audio: all 13 synthesized sound payloads matched byte-for-byte
  across two independent syntheses; a clean second build produced identical
  project.json and asset members in both archives.
- Deterministic scratch-vm replay: 659, 746, and 869 frames, each matching the
  Python reference frame-for-frame and ending in `win`.
- Static project wiring: zero unsent broadcasts, broadcasts without receivers,
  never-played sounds, never-called custom blocks, or dangling custom calls.
- Structural VM audit: zero unknown opcodes, unresolvable calls, bad input names,
  malformed assets, VM errors, or unexpected warnings.
- Menus/settings/pause/restart/quit/win-lock/mouse/master-clock checks passed;
  grounded jump SFX dispatch and SFX toggle restoration passed.
- Clone lifecycle test: eight restarts bounded to four Ground/two Far clones;
  Q removes all world clones; six bursts peak at 22 FX clones and drain to zero.
- The separate seven-run benchmark completed for all seven scenarios on both
  baseline and release archives, with no VM errors or unexpected warnings.

The menu/lifecycle and structural checks were run against both stock Scratch
and TurboWarp archives inside scratch-vm. This does not substitute for a manual
rendered-browser/device test.
