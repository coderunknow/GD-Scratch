# neon_dash / GD-Scratch v0.2.2 verification report

**Release focus:** player-reported fixes (unfair block-edge deaths, the
settings highlight cutting through the ON/OFF pills, jump/choppiness
complaints) plus real in-game settings rows: LOW LATENCY input, GRAPHICS
HIGH/LOW/ULTRA, and SHOW FPS.

**Compared baseline:** the v0.2.1 release archives (commit `7c1dda7^` tree)
and the v0.2.0 archives where the table needs three columns.

## 1. What changed

- **Block corner forgiveness (owner-directed collision-rule change).** A fall
  whose bottom sits up to `CORNER_FORGIVE = 9` px (0.3 cell) past a block's
  surface when the overlap starts now snaps on top instead of killing. Applied
  identically to the Python reference (`verify.py`, `levels.py`) and the game
  (`game.py`) — they remain transcription-equal.
- **Settings redesign: 7 rows.** MUSIC / SOUND EFFECTS / PARTICLES /
  LOW LATENCY / GRAPHICS / SHOW FPS / BACK. The highlight gets a wider
  `selWide` costume on this screen so it covers the value pill.
- **New settings** (per-run, like the existing toggles; projects cannot
  persist variables):
  - LOW LATENCY — the v0.2.1 render-cadence tap latch, now switchable. OFF =
    classic 30 Hz sampling (taps must span a physics step).
  - GRAPHICS — HIGH (default, unchanged) / LOW (far parallax layer retired,
    every particle burst halved) / ULTRA (far parallax retired, no particles).
  - SHOW FPS — a live render-fps readout (top right, ~2 updates/s) while
    playing.
- Text pool grown 48 → 56 glyph clones so the settings values (slots 1–25)
  and the FPS overlay (49–54) never collide with the play HUD (1–46).
- Tests: differential fuzzer (`tests/headless/fuzz.js` + `tools/fuzz_ref.py`),
  block-corner regression in `physics.js`, settings/graphics/latency coverage
  in `menus.js`, `level1_detail_low` benchmark scenario.

Gameplay (levels, jump/pad/orb/portal physics, speed) is unchanged except the
single forgiveness rule above; all three solver solutions still replay
frame-exactly at 30 and 60 fps.

## 2. Stability fixes

### Owner-reported: deaths at block edges with "no spike touched"

```text
Issue:       Dying when landing next to / on a block platform edge, even
             though no hazard was visibly touched.
Reproduction: Level 1 fixture solution + one extra tap on step 271: the cube
             falls onto a block corner with its bottom 2.4 px below the
             surface at step 282 and died there on the v0.2.1 rule
             (reproduced on the released v0.2.1 archive: dead@283).
Expected:    A near-miss corner clip should land, GD-style; only square wall
             hits and hits from below should kill.
Observed:    The v0.2.1 landing condition required the bottom to already be
             at/above the surface before the step (epsilon tolerance only) -
             any 1 px clip killed.
Root cause:  Designed rule was stricter than the game it imitates; the owner
             classified it as a bug (2026-09-28), which authorizes the one
             collision-rule change.
Fix:         Landing tolerance widened to CORNER_FORGIVE = 9 px in verify.py
             and mirrored in game.py. Wall hits (bottom far below the
             surface), hits while rising, and ceiling-side equivalents are
             unchanged.
Verification: The corner schedule now lands (grounded, y=-75 at step 283) and
             still wins on step 659 - asserted in physics.js at 30 and 60 fps
             against the reference trace. Differential fuzz (below) shows the
             Scratch side matches the new reference everywhere it is run.
             The three fixture replays are trace-identical to v0.2.1 (the
             rule only changes frames that used to die; solved paths never
             die), so all stored step counts and win frames hold.
```

### Owner-reported: settings highlight "not long enough"

```text
Issue:       The yellow row highlight stopped in the middle of the ON/OFF
             value pill on the settings screen.
Reproduction: Open SETTINGS; the highlight spans x=-125..+125 while the value
             pill spans x=90..162.
Root cause:  The Sel sprite used one 250 px costume for every screen.
Fix:         Second costume selWide (360 px) selected on the settings screen
             only, via a mirror variable so the costume (and the renderer
             dirty flag) only changes when the screen kind changes.
Verification: menus.js asserts currentCostume=1 (selWide) on SETTINGS and 0
             elsewhere; geometry: pill right edge 162 < 180 = selWide right
             edge. Benchmark: menu_idle redraws back to 2/frame after the
             mirror fix (3 while it switched every frame).
```

### Test-harness fixes found by the new fuzz (not game bugs)

- The fuzzer's first version advanced its input index per render frame; at
  60 fps a frame can run no physics step, which mis-paired the pending input
  latch with the next step's raw input. Fixed to drive by the observed frame
  counter (as physics.js already did).
- Scratch-vm keeps io keys down across greenFlag; a case ending mid-press
  broke the next case's menu navigation. Fixed by force-releasing keys before
  each restart. (Holding a key across a real green-flag press behaves the same
  as v0.2.1; no player-facing change was made.)

## 3. Runtime bugs

### Confirmed and fixed

- Settings highlight width (above); the collision rule change (above).

### Investigated but not defects

- Death particles were suspected missing during the audit: the Fx sprite does
  spawn bursts (verified by target dumps; my first test filtered on a wrong
  sprite name and a non-existent `isClone` property - both test bugs, fixed).
  With GRAPHICS=ULTRA zero particles are correct behavior.
- The jump branch itself performs no extra work (one SFX broadcast); no
  per-jump interpreter spike exists. The reported choppiness is renderer-side
  load, addressed with the GRAPHICS settings (below).

### Known remaining limitations

- TurboWarp's own CBF / fps / interpolation knobs live in the player, not the
  project; LOW LATENCY is the in-project analog (render-cadence tap
  sampling), and SHOW FPS displays the host's render cadence - it cannot set
  a target.
- Settings are per-run (Scratch projects cannot persist variables without
  extensions).
- Toggling GRAPHICS to HIGH mid-level does not respawn the far parallax until
  the next level start/restart; LOW/ULTRA take effect immediately.
- Rendered smoothness, audio output and real-device frame rates remain
  unmeasurable headless (no renderer/audio engine in the harness).

## 4. The new settings in detail

| Row | Values | Effect |
|---|---|---|
| MUSIC / SOUND EFFECTS / PARTICLES | ON / OFF | unchanged from v0.2.0 |
| LOW LATENCY | ON / OFF | ON: taps are latched at render cadence and consumed by exactly one physics step (default, v0.2.1 behavior). OFF: inputs are sampled at 30 Hz only - a tap shorter than a physics step is dropped. |
| GRAPHICS | HIGH / LOW / ULTRA | LOW retires the far parallax layer (2 clones) and halves every particle burst; ULTRA additionally disables particles entirely. |
| SHOW FPS | ON / OFF | draws `FPS n` (rounded, ~0.5 s averaging window) at the top right during play. |

All rows take effect immediately (except the HIGH parallax respawn noted
above) and reset to defaults on the green flag.

## 5. Benchmark results

Same method as v0.2.1 (bench.js, 7 runs, medians of run medians; exact
primitive counts from the instrumented pass; identical deterministic inputs;
headless, so renderer savings are NOT visible in these numbers).

| Scenario | prim calls/frame v0.2.1 → v0.2.2 | redraws/frame | peak clones | median ms |
|---|---:|---:|---:|---:|
| Menu idle | 535.4 → 590.2 (+10.2%) | 2.0 → 2.0 | 50 → 58 | 0.142 |
| Level 1 replay | 1,642.5 → 1,723.3 (+4.9%) | 25.2 → 25.2 | 68 → 76 | 0.323 |
| Level 3 replay | 1,625.0 → 1,706.4 (+5.0%) | 25.0 → 24.9 | 69 → 77 | 0.308 |
| Restart stress | 1,709.0 → 1,796.2 (+5.1%) | 23.5 → 23.5 | 64 → 72 | 0.419 |
| Death cycle | 1,192.6 → 1,269.0 (+6.4%) | 42.1 → 41.8 | 79 → 87 | 0.278 |
| Pause cycle | 984.2 → 1,052.6 (+6.9%) | 31.3 → 30.6 | 78 → 86 | 0.182 |
| Menu return | 549.8 → 619.5 (+12.7%) | 3.3 → 2.6 | 56 → 63 | 0.106 |
| Level 1, GRAPHICS LOW | — (new scenario) | 23.1 | 74 | 0.300 |

Honest accounting: the new features **cost** 5–13% interpreter work per frame
(8 more always-alive glyph clones for the wider text pool, the fps meter, the
settings rows). Against v0.2.0 the release is still far ahead (menu idle
−39%, level replays −36%). GRAPHICS=LOW saves little interpreter work (~2%)
because the far layer's interpreter cost is small — its real saving is
renderer-side (two fewer wide sprites to composite every frame, half the
particle clones on every burst), which is exactly the cost headless cannot
measure and the practical lever for weak devices. ULTRA also removes all
particle clones. Peak clones stay ≤87, well under the 300 limit.
